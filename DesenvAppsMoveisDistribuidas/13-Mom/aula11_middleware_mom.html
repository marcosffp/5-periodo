Fundamentos O Problema que o Middleware Resolve

Definição: Middleware é uma camada de software entre o sistema operacional e as aplicações distribuídas, fornecendo abstrações de alto nível para comunicação, nomeação, segurança, tolerância a falhas e gerenciamento de dados — ocultando a heterogeneidade da plataforma subjacente.

Transparência de Acesso

Chamadas locais e remotas têm a mesma sintaxe. O programador não diferencia onde o objeto reside.

Transparência de Localização

A aplicação não precisa saber o IP do serviço — o middleware resolve o nome.

Independência de Plataforma

Um cliente Java pode comunicar-se com um serviço Python graças ao middleware.

COULOURIS, G. et al. op. cit. Cap. 5. | BERNSTEIN, P. A. Middleware: A Model for Distributed System Services. Commun. ACM, v. 39, n. 2, pp. 86–98, 1996. DOI: 10.1145/230798.230809

ORB Object Request Broker — CORBA, IDL e o Padrão OMG

O OMG padronizou em 1991 a arquitetura CORBA para que objetos distribuídos se invoquem independentemente de linguagem ou SO. O coração é o ORB, que roteia cada invocação via protocolo IIOP.

Exemplo de IDL CORBA

Conta.idl CORBA IDL 
// IDL é neutro: compila para stub Java + skeleton C++
interface Conta {
    double  getSaldo();
    void    depositar(in double valor);
    boolean sacar(in double valor);
};

O compilador IDL gera o Stub (cliente) e o Skeleton (servidor) — o dev implementa só a lógica.

1989
Fundação do OMG
Object Management Group criado para padronizar computação distribuída orientada a objetos.
1991
CORBA 1.0
Primeira especificação. Introduz IDL independente de linguagem e o conceito de ORB.
1996
CORBA 2.0 — IIOP
Internet Inter-ORB Protocol: interoperabilidade entre ORBs distintos via TCP/IP.
2000s
Declínio e legado
Complexidade cede espaço a REST e gRPC. O conceito de IDL + stubs é adotado pelo Protobuf e Apache Thrift.

Stub vs. Skeleton: o stub fica no cliente — simula o objeto remoto localmente. O skeleton fica no servidor — recebe a chamada do ORB e invoca a implementação real. Confundir os dois é o erro mais comum em provas.

VINOSKI, S. CORBA: Integrating Diverse Applications Within Distributed Heterogeneous Environments. IEEE Communications Magazine, v. 35, n. 2, pp. 46–55, fev. 1997. | COULOURIS et al. op. cit. Cap. 5.

MOM Message-Oriented Middleware — Desacoplamento Total

Princípio central (Eugster et al., 2003): O MOM promove desacoplamento triplo: de espaço (não se conhecem por endereço), de tempo (não precisam estar ativos simultaneamente) e de sincronização (não se bloqueiam mutuamente).

❌ RPC: Chamada Síncrona (acoplado)

✅ MOM: Mensagem Assíncrona (desacoplado)

⏱ Tempo

Consumidor pode estar offline. Mensagem fica no broker até ser processada.

📍 Espaço

Produtor não conhece endereço do consumidor. Zero acoplamento de IP/endpoint.

🔄 Sincronização

Produtor não bloqueia esperando resposta. Envia e continua.

EUGSTER, P. T. et al. The Many Faces of Publish/Subscribe. ACM Computing Surveys, v. 35, n. 2, pp. 114–131, jun. 2003. DOI: 10.1145/857076.857078

MOM Dois Modelos: Filas de Mensagens vs. Tópicos Pub/Sub

📬 Filas (Point-to-Point)

Uma mensagem tem exatamente um consumidor. Após leitura, é removida. Garante processamento único.

Uso: processamento de pedidos, job queues, tarefas background

📡 Tópicos (Pub/Sub)

Mensagem entregue a todos os assinantes. Cada um recebe cópia. Produtor não conhece quem consome.

Uso: notificações em tempo real, múltiplos serviços downstream
CaracterísticaFila (P2P)Tópico (Pub/Sub)
DestinatáriosExatamente 1N assinantes
Msg após consumoRemovidaMantida (retenção configurável)
DurabilidadeAlta — reprocessamentoVariável por assinante
EUGSTER, P. T. et al. op. cit. DOI: 10.1145/857076.857078 | COULOURIS et al. op. cit. Cap. 5.

RabbitMQ Arquitetura e Padrões de Roteamento

RabbitMQ implementa AMQP 0-9-1. Modelo de roteamento: Producer → Exchange → Binding → Queue → Consumer.

Tipos de Exchange

Direct Exchange

Roteia para a fila cuja binding key = routing key exata. Ex.: order.created → Queue A.

Fanout Exchange

Ignora routing key. Distribui cópia a todas as filas vinculadas. Padrão broadcast.

Topic Exchange

Roteamento por padrão com curinga: order.* e #.critical.

Headers Exchange

Roteamento por atributos do cabeçalho AMQP, sem usar routing key.

RABBITMQ TEAM. RabbitMQ: AMQP Concepts. Disponível em: <https://www.rabbitmq.com/tutorials/amqp-concepts>. Acesso: jun. 2026. | JOHANSSON, M. RabbitMQ Essentials. 2. ed. Packt, 2020.

Kafka Apache Kafka — Log Distribuído como Infraestrutura

Origem (Kreps et al., 2011): Kafka foi criado no LinkedIn para processar bilhões de eventos de log por dia com latência de segundos. Diferente de um MOM clássico, seu modelo central é um log de commit distribuído imutável, não uma fila de destruição.

A Abstração do Log

Mensagens são escritas em sequência num log imutável particionado. Cada consumer controla seu próprio offset — pode reler, processar em paralelo ou retroceder. Impossível num MOM clássico.

Componentes Principais

Producer
Publica em tópicos. Escolhe partição por chave ou round-robin.
Consumer Group
Cada partição vai a exatamente 1 membro. Paralelismo automático.
Broker / Cluster
Armazena partições. Réplicas garantem durabilidade.
Topic + Partition
Tópico = canal lógico. Partições = paralelismo e escala horizontal.

Throughput — o contexto importa

Os números variam com hardware, fator de replicação, tamanho da mensagem e política de ACK. Kafka é projetado para alto volume contínuo; RabbitMQ para roteamento inteligente. Avalie com benchmark no seu próprio workload — não use números genéricos para decidir.

KREPS, J.; NARKHEDE, N.; RAO, J. Kafka: A Distributed Messaging System for Log Processing. In: NetDB Workshop (co-located VLDB), Seattle, 2011. | KLEPPMANN, M. Designing Data-Intensive Applications. Cap. 11. O'Reilly, 2017.

🐰 Use RabbitMQ quando…

  • Roteamento complexo por routing key, headers ou padrões
  • Task queue — cada tarefa processada exatamente 1×
  • Mensagens com TTL ou prioridade
  • DLQ e retry granular com dead-letter exchange

⚡ Use Kafka quando…

  • Alto throughput contínuo (telemetria, log, clickstream)
  • Múltiplos sistemas precisam reler os mesmos eventos
  • Event sourcing ou CQRS
  • Integração de dados — CDC com Kafka Connect

Padrões Padrões Arquiteturais com Message-Oriented Middleware

⚔️ Competing Consumers

Múltiplos workers competem pelas mensagens de uma fila. Cada mensagem vai a exatamente um. Escala horizontal de workers.

📡 Event-Driven Architecture (EDA)

Serviços comunicam-se apenas por eventos em tópicos. Nenhum sabe da existência dos outros — máximo desacoplamento.

💀 Dead Letter Queue (DLQ)

Mensagens não processadas (erro, expiradas, rejeitadas) vão para fila especial. Essencial para produção — evita perda silenciosa de dados.

Fila Principal → ❌ falha N tentativas → DLQ → 🔍 análise / reprocessamento

🗂 CQRS + Event Sourcing

Separação leitura (Query) / escrita (Command). Eventos armazenados como log imutável. Estado derivado pela reprodução de eventos. Kafka é a plataforma natural.

Command → Event Store (Kafka) → Projections → Query Models
FOWLER, M.; LEWIS, J. Microservices. 2014. martinfowler.com/articles/microservices.html | RICHARDSON, C. Microservices Patterns. Manning, 2018. Cap. 3–4.

🛠 Exercício: Escolha Arquitetural — E-commerce

Cenário: E-commerce com: OrderService, StockService, EmailService, PaymentService, AuditService. O time debate a tecnologia de comunicação entre eles.

8:00

📋 Requisitos

  • Pedido criado → Stock reserva E Email confirma
  • Picos de 50 000 pedidos/min na Black Friday
  • AuditService relê os últimos 30 dias para compliance
  • Pagamentos com falha: 3 retentativas → DLQ
  • Relatórios em tempo real de pedidos/min

🔍 Questões

  1. "Pedido criado" deve chegar ao Stock E ao Email: fila ou tópico?
  2. RabbitMQ ou Kafka? Justifique com throughput e reprocessamento.
  3. Como implementar retry + DLQ para o PaymentService?

1. Tópico (Pub/Sub)

"Pedido criado" precisa alcançar múltiplos serviços. Fila P2P entregaria a apenas um. Tópico garante cópia independente para cada assinante.

2. Kafka é mais adequado

Alto throughput (50k/min), consumer groups independentes (Audit relê 30d sem afetar outros), streaming de relatórios em tempo real. RabbitMQ seria suficiente apenas para a DLQ de pagamentos.

3. Retry + DLQ

Kafka: retry topics (payment-retry-1/2/3) com backoff exponencial → após 3 falhas, publica em payment-dlq. RabbitMQ: configure x-dead-letter-exchange com TTL por tentativa e max-retries no consumer.

KLEPPMANN, M. op. cit. Cap. 11. | RICHARDSON, C. op. cit.

Síntese da Aula

📌 Conceitos-Chave

  • Middleware: camada entre SO e apps; abstrai heterogeneidade
  • ORB/CORBA: IDL neutra gera stub (cliente) e skeleton (servidor)
  • MOM: desacoplamento triplo — espaço, tempo e sincronização
  • Filas (P2P): cada mensagem processada exatamente 1×
  • Tópicos (Pub/Sub): múltiplos assinantes, cópias independentes
  • RabbitMQ: Exchange + Binding + Queue + AMQP + DLQ
  • Kafka: log imutável, partições, consumer groups, retenção

⚠️ Armadilhas Comuns

  • Usar fila P2P quando múltiplos serviços precisam do evento → use tópico
  • Não configurar DLQ → falhas silenciosas em produção
  • Escolher Kafka para workloads simples → overhead operacional
  • Kafka garante ordem por partição, não globalmente
  • Tratar Kafka como banco de dados primário — é log, não SGBD
  • Confundir stub (cliente) com skeleton (servidor) no CORBA
