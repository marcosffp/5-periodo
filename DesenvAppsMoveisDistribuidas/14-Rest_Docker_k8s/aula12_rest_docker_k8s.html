🏭 Roteiro da aula

REST define como uma API deve se comportar. OpenAPI define como documentá-la. Docker e Kubernetes definem como operá-la em produção com confiança. Os três temas são independentes, mas se completam na prática de qualquer time de desenvolvimento distribuído.

I. REST O problema que REST resolve

Integração antes de REST

Anos 1990–2000: Web Services SOAP

Cada sistema definia seus próprios formatos de mensagem e protocolos. Integrar dois sistemas exigia negociação de WSDL, schemas XML e stubs gerados. Uma operação simples resultava em envelopes SOAP com dezenas de linhas e qualquer mudança no contrato quebrava todos os clientes.

O problema central

Sem padrão, cada par de sistemas que precisava se comunicar era um projeto de integração separado. O custo de escalar o número de integrações crescia quadraticamente com o número de sistemas.

A proposta de Fielding (2000)

"REST is intended to evoke an image of how a well-designed Web application behaves: a network of web pages where the user progresses through an application by selecting links."

FIELDING, R. T. Architectural Styles and the Design of Network-based Software Architectures. UC Irvine, 2000, Cap. 5.

A ideia central

Usar o próprio HTTP como linguagem universal de integração. Recursos identificados por URIs, operações pelos verbos HTTP, representações em JSON ou XML. A Web já funcionava assim, ou seja, REST formalizou os princípios como um estilo arquitetural.

REST não é um padrão, é um estilo arquitetural

Não há organização que certifique uma API como "REST". REST é um conjunto de constraints que, quando satisfeitos, produzem as propriedades desejadas de escalabilidade, visibilidade e modificabilidade.

FIELDING, R. T. Architectural Styles and the Design of Network-based Software Architectures. Dissertação de Doutorado. University of California, Irvine, 2000. Disponível em: https://ics.uci.edu/~fielding/pubs/dissertation/top.htm

I. REST Os 6 constraints arquiteturais de Fielding

1. Client–Server

Separação de responsabilidades: o cliente gerencia a interface; o servidor gerencia dados e lógica de negócio. Cada lado pode evoluir independentemente. O app mobile não precisa saber nada sobre o banco de dados do servidor.

2. Stateless

Cada requisição deve conter todas as informações necessárias para ser processada. O servidor não mantém estado de sessão entre requisições. Consequência direta: qualquer instância do servidor pode atender qualquer requisição, tornando o escalonamento horizontal trivial.

3. Cache

Respostas devem declarar explicitamente se são cacheáveis (Cache-Control, ETag, Last-Modified). Um cliente ou intermediário que cacheia respostas reduz a latência e a carga sobre o servidor.

4. Uniform Interface (o mais importante)

Quatro sub-constraints: (a) identificação de recursos por URI; (b) manipulação via representações; (c) mensagens auto-descritivas (Content-Type, status code); (d) HATEOAS — hipermídia como motor do estado da aplicação.

5. Layered System

O cliente não sabe se está se comunicando com o servidor final ou com um intermediário (API Gateway, proxy reverso, CDN, load balancer). Cada camada vê apenas a camada imediatamente adjacente.

6. Code-on-Demand (opcional)

O servidor pode estender a funcionalidade do cliente enviando código executável (ex: JavaScript). O único constraint opcional. Usado em aplicações web; raro em APIs de sistemas distribuídos.

FIELDING, R. T. Architectural Styles and the Design of Network-based Software Architectures. UC Irvine, 2000, Cap. 5.1–5.3. | RICHARDSON, L.; RUBY, S. RESTful Web Services. O'Reilly, 2007.

URIs identificam recursos, não ações

/cancelOrder/123 viola o Uniform Interface. O correto é POST /orders/123/cancellations — a ação é o verbo, o recurso é o substantivo.

Estratégias de versionamento

URI Versioning (mais adotado)

/v1/orders  →  /v2/orders

Visível e fácil de testar no browser. Adotado por Stripe, GitHub, Twitter/X. Desvantagem: viola o princípio REST de que URIs identificam recursos (a versão é um detalhe de implementação, não parte do recurso).

Header Versioning

Accept: application/vnd.app.v2+json

Mais fiel ao REST. A URI do recurso não muda. Mais difícil de testar e de cachear em proxies. Adotado pelo GitHub API v3 e Microsoft Graph.

Regra prática

Versione desde a primeira release pública. Nunca quebre contratos existentes sem um período de transição explícito e documentado.

MASSE, M. REST API Design Rulebook. O'Reilly, 2011. | RICHARDSON, L.; AMUNDSEN, M.; RUBY, S. RESTful Web APIs. O'Reilly, 2013.

I. REST Idempotência e segurança dos verbos HTTP

Dois conceitos fundamentais que determinam como clientes e intermediários podem tratar requisições com segurança.

✅ Segurança (Safe)

Um método é seguro se não altera o estado do servidor. O cliente pode chamá-lo quantas vezes quiser sem efeitos colaterais. Segurança não implica que a operação seja livre de efeitos, logs e métricas podem ser registrados mas o estado dos recursos não muda.

Métodos seguros: GET, HEAD, OPTIONS

🔄 Idempotência

Um método é idempotente se chamar N vezes produz o mesmo efeito que chamar uma vez. A propriedade é sobre o estado resultante, não sobre a resposta HTTP que pode variar (ex: primeiro DELETE retorna 204, o segundo retorna 404).

Métodos idempotentes: GET, HEAD, PUT, DELETE, OPTIONS

MétodoSeguro?Idempotente?Corpo na req?Uso típicoConsequência de repetir
GETSimSimNãoLeitura de recursoIdêntico (seguro para retry automático)
HEADSimSimNãoVerificar existência / metadadosIdêntico (sem corpo na resposta)
OPTIONSSimSimNãoListar métodos permitidos (CORS)Idêntico
PUTNãoSimSimSubstituição completa do recursoEstado final idêntico (seguro para retry)
DELETENãoSimRaramenteRemoção de recursoPrimeiro: 204. Seguintes: 404. Estado idêntico.
PATCHNãoDependeSimAtualização parcialDepende do payload (pode ou não ser idempotente)
POSTNãoNãoSimCriação de recursoCria um novo recurso a cada chamada (nunca retry automático)

Por que isso importa na prática

Um cliente que perde a resposta de um POST (timeout de rede) não pode repetir a requisição com segurança, pois a repetição pode criar um pedido duplicado. Para operações críticas não idempotentes, use chaves de idempotência (Idempotency-Key header, adotado pelo Stripe) que permitem ao servidor detectar e ignorar réplicas.

RFC 9110 — HTTP Semantics. IETF, 2022. Seções 9.2.1 (Safe) e 9.2.2 (Idempotent). DOI: 10.17487/RFC9110. | Stripe Idempotency: https://stripe.com/docs/api/idempotent_requests

Anti-padrão frequente: retornar 200 com erro no corpo

HTTP 200 OK com {"status": "error", "message": "not found"} quebra o contrato REST, impede que API Gateways e clientes tratem erros automaticamente e viola as mensagens auto-descritivas do Uniform Interface.

I. REST HATEOAS — Hipermídia como motor do estado

O sub-constraint mais ignorado

HATEOAS (Hypermedia As The Engine Of Application State) é o quarto sub-constraint do Uniform Interface. A ideia: assim como uma página web guia o usuário por links, uma API REST deve guiar o cliente pelas ações disponíveis através de links na própria resposta.

O problema sem HATEOAS

O cliente precisa conhecer antecipadamente todas as URIs e quando cada ação está disponível. Qualquer mudança no servidor (URI, transição de estado) exige atualização coordenada do cliente. O servidor e o cliente ficam acoplados.

Com HATEOAS

O cliente começa de um único ponto de entrada e descobre as ações disponíveis através das respostas. O servidor controla o fluxo. URIs podem mudar sem quebrar clientes que seguem links.

Exemplo: recurso Pedido com HATEOAS

// GET /v1/orders/42 — pedido aguardando pagamento 
{
  "id": "42",
  "status": "pending_payment",
  "total": 149.90,
  "_links": {
    "self": {
      "href": "/v1/orders/42",
      "method": "GET"
    },
    "pay": {
      "href": "/v1/orders/42/payments",
      "method": "POST"
    },
    "cancel": {
      "href": "/v1/orders/42/cancellations",
      "method": "POST"
    }
  }
}
// GET /v1/orders/42 — após pagamento confirmado
{
  "status": "paid",
  "_links": {
    "self": { "href": "/v1/orders/42" },
    "track": {
      "href": "/v1/orders/42/tracking",
      "method": "GET"
    }
    // "cancel" e "pay" não aparecem mais
  }
}

HAL e JSON:API

Dois formatos populares que padronizam como expressar HATEOAS em JSON: HAL (Hypertext Application Language) usa _links; JSON:API usa links e relationships.

I. REST Autenticação em APIs REST — Bearer Token e OAuth2

Bearer Token (JWT)

O mecanismo mais comum em APIs REST. O cliente envia um token opaco ou estruturado (JWT) no header de cada requisição. O servidor valida o token sem consultar banco de dados (o que respeita o constraint Stateless).

# Formato do header em toda requisição autenticada
Authorization: Bearer eyJhbGciOiJSUzI1NiJ9...

# Estrutura do JWT (3 partes separadas por ponto)
Header:  { "alg": "RS256", "typ": "JWT" }
Payload: {
  "sub": "user:u42",
  "roles": ["admin"],
  "exp": 1750000000  # Unix timestamp
}
Signature: RSASHA256(base64(header) + "."
              + base64(payload), privateKey)

JWT não é criptografia, é assinatura

O payload é apenas codificado em Base64, não cifrado. Nunca armazene dados sensíveis (senhas, cartões) no JWT. Use JWE se precisar de confidencialidade.

OAuth 2.0 — fluxos principais

OAuth2 é um framework de autorização

Permite que um sistema acesse recursos em nome de um usuário sem receber suas credenciais. Define quatro fluxos para diferentes cenários.

Client Credentials (M2M)

1

Serviço A envia client_id + client_secret para o Authorization Server

2

Authorization Server retorna um access_token (JWT) com escopo definido

3

Serviço A usa o token como Bearer em chamadas ao Serviço B

Authorization Code (usuário final)

1

App redireciona usuário ao Authorization Server (ex: "Login com Google")

2

Usuário autentica e consente. Authorization Server retorna um code

3

App troca o code por access_token + refresh_token em chamada server-to-server

4

App usa access_token como Bearer. Quando expira, usa refresh_token para renovar sem novo login

RFC 6749 — The OAuth 2.0 Authorization Framework. IETF, 2012. DOI: 10.17487/RFC6749. | RFC 7519 — JSON Web Token (JWT). IETF, 2015. DOI: 10.17487/RFC7519. | RFC 7617 — The 'Basic' HTTP Authentication Scheme. IETF, 2015.

II. OpenAPI Documento OpenAPI 3.1 — estrutura e schemas

Por que documentação como código

Sem contrato formal

Dois times integram sistemas via e-mail e planilhas. Um campo muda de tipo. O consumer quebra em produção. A investigação leva horas. Com um documento OpenAPI versionado no repositório, a mudança é visível em PR antes de ir ao ar.

OpenAPI Specification (OAS)

Formato YAML/JSON que descreve completamente uma API REST. Evolução do Swagger Specification, hoje mantido pela Linux Foundation. A versão 3.1 alinha os schemas com o JSON Schema 2020-12.

Schemas com composição

components:
  schemas:
    BaseOrder:
      properties:
        id: {type: string, format: uuid}
        created_at: {type: string,
                       format: date-time}

    Order:
      allOf:          # herança de schema
        - $ref: '#/components/schemas/BaseOrder'
        - properties:
            status:
              type: string
              enum: [pending, paid, shipped]
            total: {type: number}

    PaymentMethod:
      oneOf:          # polimorfismo
        - $ref: '#/components/schemas/CreditCard'
        - $ref: '#/components/schemas/Pix'
      discriminator:
        propertyName: type

Segurança no documento (securitySchemes)

components:
  securitySchemes:
    BearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT

    OAuth2:
      type: oauth2
      flows:
        authorizationCode:
          authorizationUrl: https://auth.app.io/oauth/authorize
          tokenUrl: https://auth.app.io/oauth/token
          scopes:
            orders:read: Leitura de pedidos
            orders:write: Criação e edição de pedidos

# Aplicando segurança a um endpoint específico
paths:
  /orders:
    post:
      security:
        - OAuth2: [orders:write]

O Swagger UI lê os securitySchemes

Com os schemas declarados, o Swagger UI exibe um botão "Authorize" que permite ao desenvolvedor inserir seu token e testar endpoints protegidos diretamente na interface, sem precisar de curl ou Postman.

🎯 Checkpoint I — REST e OpenAPI

Questão 1 — Idempotência e segurança

Um cliente perde a resposta de uma requisição DELETE /orders/99 por timeout de rede e não sabe se o servidor processou. Ele pode repetir a requisição automaticamente sem risco? E um POST /orders pode receber o mesmo tratamento? Justifique com base nas propriedades dos métodos HTTP.

A) Nenhum dos dois pode ser repetido automaticamente. DELETE e POST são ambos métodos não seguros — qualquer operação que modifique estado no servidor exige confirmação manual antes de ser retentada, independentemente da idempotência.
B) O DELETE pode ser repetido automaticamente: é idempotente por definição (RFC 9110). O estado resultante é idêntico — o recurso não existe em ambos os casos, mesmo que a segunda chamada retorne 404. O POST não pode: não é idempotente, e repetições criam novos recursos. Para POST, a solução é o header Idempotency-Key, que permite ao servidor detectar e ignorar retransmissões.
C) O POST pode ser repetido porque o cliente pode usar o mesmo corpo de requisição, garantindo que o servidor crie o mesmo recurso. O DELETE não pode ser repetido porque após o primeiro DELETE o recurso não existe mais, e a segunda chamada retornaria 404, indicando falha.
D) Ambos podem ser repetidos automaticamente desde que o cliente inclua o header X-Retry: true, que sinaliza ao servidor que a requisição é uma retentativa e permite que ele aplique deduplicação independentemente do método HTTP utilizado.

Questão 2 — HATEOAS e OpenAPI

A resposta de GET /orders/42 inclui um link "cancel" quando o pedido está pendente, e não inclui esse link quando já foi pago. Um desenvolvedor argumenta que isso é desnecessário — o cliente pode simplesmente tentar o DELETE e tratar o 409. Por que a abordagem HATEOAS é arquiteturalmente superior?

A) A abordagem HATEOAS é superior porque reduz o tráfego de rede: o cliente faz menos chamadas ao servidor, pois sabe antecipadamente quais ações estão disponíveis sem precisar tentar e receber erros.
B) A abordagem HATEOAS é preferível principalmente por razões de segurança: ocultar o link de cancelamento impede que usuários mal-intencionados descubram a URI e tentem acessá-la diretamente via ferramentas como curl.
C) Com HATEOAS, o servidor controla as transições de estado válidas — o cliente não precisa conhecer as regras de negócio para saber o que pode fazer em cada estado. Se as regras mudarem (ex: janela de cancelamento cair de 24h para 12h), o servidor muda os links e o cliente se adapta automaticamente, sem deploy. A abordagem "tente e trate o 409" acopla o cliente ao conhecimento das regras de estado do servidor, e qualquer mudança nessas regras exige atualização coordenada do cliente.
D) HATEOAS é superior porque o OpenAPI não consegue documentar respostas condicionais com campos que aparecem em alguns estados e não em outros, então incluir os links na resposta é a única forma de comunicar ao cliente quais ações estão disponíveis no momento.

III. Docker Contêineres, Dockerfile e boas práticas

Por que contêineres

O problema clássico

O serviço roda Python 3.11 localmente. O servidor de produção tem Python 3.9 e uma versão diferente de libffi. O deploy quebra. Um contêiner empacota código, runtime e dependências numa unidade portável que roda identicamente em qualquer máquina com Docker Engine.

Contêiner ≠ Máquina Virtual

VMs virtualizam hardware completo com kernel próprio. Contêineres compartilham o kernel do host, isolando apenas processo e filesystem. Inicializam em milissegundos, consomem megabytes.

Dockerfile com multi-stage build

# Estágio 1: builder — compila e testa
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json .
RUN npm ci
COPY . .
RUN npm run build && npm test

# Estágio 2: produção — só o necessário
FROM node:22-alpine AS production
WORKDIR /app
COPY package*.json .
RUN npm ci --omit=dev
COPY --from=builder /app/dist ./dist
USER node         # nunca rodar como root
EXPOSE 3000
CMD ["node", "dist/main.js"]

Docker Compose — múltiplos serviços locais

services:

  api:
    build:
      context: ./api
      target: production  # estágio alvo
    ports: ["3000:3000"]
    environment:
      DATABASE_URL: postgresql://app:app@db/appdb
      REDIS_URL: redis://cache:6379
      JWT_SECRET: ${JWT_SECRET}  # do .env
    depends_on:
      db: {condition: service_healthy}
      cache: {condition: service_started}

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: app
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD", "pg_isready"]
      interval: 5s

  cache:
    image: redis:7-alpine

volumes: {pgdata: {}}

Multi-stage + Compose: boas práticas integradas

O multi-stage build garante que a imagem de produção não contém ferramentas de build nem dependências de dev. O healthcheck no Compose evita que a API suba antes do banco estar pronto.

Liveness e Readiness Probes

Duas probes, dois propósitos distintos

Liveness: "o contêiner está travado?" — se falhar, K8s reinicia o Pod.
Readiness: "o contêiner está pronto para receber tráfego?" — se falhar, K8s remove o Pod do Service (sem matar).

livenessProbe:
  httpGet:
    path: /health/live
    port: 3000
  initialDelaySeconds: 15  # aguarda inicialização
  periodSeconds: 10
  failureThreshold: 3      # 3 falhas seguidas = restart

readinessProbe:
  httpGet:
    path: /health/ready
    port: 3000
  periodSeconds: 5
  failureThreshold: 2      # 2 falhas = sai do LB
 
// /health/ready — verifica dependências
app.get('/health/ready', async (req, res) => {
  const dbOk = await db.ping();
  const cacheOk = await redis.ping();
  if (dbOk && cacheOk)
    res.status(200).json({ status: 'ready' });
  else
    res.status(503).json({ status: 'not ready' });
});

IV. Kubernetes HorizontalPodAutoscaler e visão geral

Escalonamento automático com HPA

kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef:
    kind: Deployment
    name: orders-api
  minReplicas: 2
  maxReplicas: 12
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60

Como o HPA decide

A cada 15 segundos, o HPA consulta as métricas de CPU de todos os Pods do Deployment. Se a utilização média superar 60%, calcula o número de réplicas necessárias: réplicas = ceil(atual × utilização / alvo). Com 3 Pods a 90% de CPU, o resultado seria ceil(3 × 90/60) = 5 réplicas.

Pré-requisito crítico: resource requests

O HPA só funciona se o Deployment tiver resources.requests.cpu definido. Sem isso, o K8s não tem base para calcular o percentual de utilização.

🎯 Checkpoint II — Docker e Kubernetes

Questão 3 — Multi-stage build

O Dockerfile usa multi-stage build com um estágio builder (que compila e testa) e um estágio production (que copia apenas o artefato compilado). Qual é o benefício concreto dessa separação em relação a um Dockerfile de estágio único que faz tudo?

A) O multi-stage build é mais rápido porque executa o estágio de build e o de produção em paralelo, aproveitando múltiplos núcleos do host durante o processo de construção da imagem.
B) A imagem final de produção contém apenas o artefato compilado e as dependências de runtime — sem compilador, ferramentas de build, dependências de dev ou código-fonte. Isso reduz drasticamente a superfície de ataque (menos binários que podem ser explorados) e o tamanho da imagem (que pode cair de centenas para dezenas de MB), acelerando pulls no deploy.
C) O multi-stage build permite que a imagem de produção seja executada sem o Docker Engine instalado no servidor, pois o estágio builder compila todos os binários necessários para execução direta no sistema operacional do host.
D) A principal vantagem é o cache de camadas: o Docker armazena o resultado do estágio builder em cache e reutiliza na próxima execução, eliminando a necessidade de recompilar o código mesmo que as dependências tenham mudado.

Questão 4 — Liveness vs. Readiness

O Pod da Orders API está rodando, mas o banco de dados ficou temporariamente indisponível. A readinessProbe falha. A livenessProbe continua passando. O que o Kubernetes faz e por que esse comportamento é correto?

A) O Kubernetes reinicia o Pod porque interpreta a falha da readinessProbe como indicação de que o processo está em estado irrecuperável, aplicando a mesma política de recuperação usada para a livenessProbe.
B) O Kubernetes remove o Pod do balanceamento de carga do Service (parar de enviar tráfego), mas mantém o contêiner rodando. Quando o banco voltar, a readinessProbe passa novamente e o Pod retorna ao pool. Esse comportamento é correto: o processo da API não está travado (liveness OK), apenas incapaz de atender requisições sem o banco (readiness falhou). Reiniciar o Pod não resolveria o problema — o banco continuaria indisponível.
C) O Kubernetes aguarda 3 falhas consecutivas da readinessProbe e, após atingir o failureThreshold, encerra o Pod e cria um novo, assumindo que a reinicialização pode resolver dependências de rede temporárias entre o contêiner e o banco de dados.
D) O Kubernetes não toma nenhuma ação automática quando apenas a readinessProbe falha. O comportamento de remover o Pod do Service só ocorre quando ambas as probes (liveness e readiness) falham simultaneamente por pelo menos 5 minutos.

Pontos para levar

REST é um estilo arquitetural, não uma tecnologia

A maioria das APIs chamadas de "REST" viola Stateless ou Uniform Interface. Conhecer os 6 constraints e a semântica dos verbos permite avaliar e projetar APIs com fundamento — e perceber quando um colega está criando um anti-padrão.

Idempotência é contrato, não implementação

GET e DELETE podem ser repetidos com segurança. POST não pode. Essa distinção determina como clientes implementam retry, como load balancers roteiam e como a Idempotency-Key protege operações críticas.

Liveness ≠ Readiness

Reiniciar um Pod que perdeu conexão com o banco não resolve nada — o banco continua indisponível. Readiness retira o Pod do balanceamento até as dependências voltarem. Liveness reinicia apenas quando o processo está irrecuperável.
